# audioEngine.js

Owns the single `AudioContext`, the master gain, the live [synthEngine](./synthEngine.md) and the [mixer](./mixer.md). All of them are created lazily in `ensureContext()`.

**Fixed 48 kHz engine rate** (`ENGINE_SAMPLE_RATE`): the context is created with `{ sampleRate: 48000 }` rather than the output device's native rate, and Chrome resamples to the device. On a 192 kHz device every node costs about 4× as much. Measured offline, the demo song's effect chains alone (no notes) needed 109% of real time at 192 kHz versus 14% at 48 kHz, and the densest section needed 241% versus about 50%. The overloaded audio thread produced total silence while the clock still advanced. Don't remove this without re-measuring.

**Autoplay policy:** Chrome only lets a context start inside a user gesture. A context created or resumed outside one stays suspended with a frozen `currentTime`, and every attempt logs "The AudioContext was not allowed to start". So:
- `ensureContext()` never resumes.
- `unlockAudio()` is the only place that resumes. It runs from capture-phase `mousedown`/`click`/`keydown`/`touchend` listeners on `window`, so it fires before the Play button, Space or a computer-keyboard note handles the same gesture. The listeners stay registered because Chrome can suspend a context again. **Not `pointerdown`:** for a mouse, Chrome dispatches `pointerdown` *before* it records the user activation (that happens at `mousedown`), so audio started there is refused. This was the second half of the silent-playback bug, and it's invisible in the preview pane.
- **Nothing touches audio before the page has user activation** (`navigator.userActivation.hasBeenActive`): `unlockAudio`, live notes and pitch bend all return early. There's no context at page load (see [transportController.js](../core/transportController.md)), and a MIDI note before any click is dropped, since it couldn't sound anyway.
- `getAudioState()` returns `"not-started"` or the context's state, and `audio:state` is emitted on every context state change. [transportBar.js](../ui/transportBar.md) uses it to show a warning whenever audio exists but isn't running.

Before this fix the context was created at startup and only resumed as a side effect of scheduling sounds from timers. In a real Chrome tab playback ran against a frozen clock after the first click. The preview pane doesn't enforce autoplay, which is why earlier testing missed it.

- **Live notes:** subscribes to `note:on`/`note:off` on the [eventBus](../core/eventBus.md). A note-on plays the **selected track's** patch through that track's mixer bus (via [selection.js](../core/selection.md)), so live MIDI, computer-keyboard and piano-roll previews sound exactly like that track's playback, including its effects, volume and pan. It falls back to a default patch on the master bus only when the project has no tracks.
- **Live patch edits:** `patch:param-changed` (from `setTrackPatchParam`) → `synthEngine.refreshPatch(patch)`, so sounding notes follow slider and MIDI-CC edits.
- **Pitch bend:** `midi:pitchbend` (14-bit, centred on 0 after parsing) → `synthEngine.setPitchBend`, ±200 cents on live voices only.
- **Sequenced notes:** `scheduleNote(note, velocity, startTime, durationSeconds, patch, destination)` (used by [transportController.js](../core/transportController.md)) and `cancelScheduledNotes()` (called on transport stop/pause/seek).
- **Model -> audio sync:** `attachProject(project)` stores the project, and every `project:changed` queues a `mixer.syncProject(project)` coalesced to one per microtask. The mixer is also synced the moment it's created. UI code never touches the mixer. It only mutates the project through [project.js](../core/project.md).
- **Metering:** when the context is created, a channel splitter + two `AnalyserNode`s tap `mixer.masterOutput`. `getMasterAnalysers()` returns them, or `null` before audio exists (non-creating, for [levelMeter.js](../ui/levelMeter.md)).
- `ensureAudioContext()`/`getMasterGain()`/`getMixer()`: accessors for modules that need the same context/graph.

**Audio buffer setting (2026-10-15):** `getLatencyMode()`/`setLatencyMode()` keep a `latencyHint` of `"interactive"` (default) or `"playback"` in `localStorage` (`synthdaw.audioLatency`), applied when the context is created. "playback" asks Chrome for a larger output buffer, which rides out CPU spikes (JIT warm-up, GC, a busy machine, resampling to a 192 kHz device) at the cost of more latency for live notes. [projectControls.js](../ui/projectControls.md) offers it as an **Audio** picker and reloads the page to apply it, since the graph is built on the context.
