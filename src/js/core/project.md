# project.js

The project data model: `Project { tempo, timeSignature: { beatsPerBar }, tracks: [] }`, `Track { id, name, blocks: [] }`, `Block { id, startBeat, lengthBeats, notes: [] }`, `Note { id, note (MIDI number), startBeat (relative to the block), lengthBeats, velocity }`. Plain data, no Web Audio/DOM references — mutated in place by the exported functions (`addTrack`, `removeTrack`, `addBlock`, `removeBlock`, `moveBlock`, `resizeBlock`, `addNote`, `removeNote`, `moveNote`, `resizeNote`) rather than returning new copies, since [timeline.js](../ui/timeline.md) and [pianoRoll.js](../ui/pianoRoll.md) both re-render from the same object after every mutation.

A note's `startBeat` is relative to its containing block, not the project timeline — [transportController.js](./transportController.md) computes the absolute position as `block.startBeat + note.startBeat` when scheduling playback. **Deviation:** every track currently plays through the one global synth patch ([patch.js](../audio/patch.md)) — there is no per-track instrument yet, so all tracks sound identical. Per-track patches are deferred; adding them means both a data-model change here (`Track.patch`) and a way to pick which track's patch the [patchEditor](../ui/patchEditor.md) is editing, which is more UI than "piano roll" scope covers.

IDs are a simple incrementing counter (`track-1`, `block-1`, `note-1`, ...), unique for the page's lifetime — fine for an in-memory single-session project, but will need revisiting once projects can be saved/reloaded (Phase 9) without ID collisions across sessions.
