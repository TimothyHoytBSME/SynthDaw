# project.js

The project data model: `Project { tempo, timeSignature: { beatsPerBar }, tracks: [], master: { volume, effects: [] }, loop: { enabled, startBeat, endBeat } }`, `Track { id, name, blocks: [], volume, pan, muted, soloed, effects: [] }`, `Block { id, startBeat, lengthBeats, notes: [] }`, `Note { id, note (MIDI number), startBeat (relative to the block), lengthBeats, velocity }`, `Effect { id, type, params: {}, bypassed }`. Plain data, no Web Audio/DOM references — mutated in place by the exported functions rather than returning new copies, since [timeline.js](../ui/timeline.md), [pianoRoll.js](../ui/pianoRoll.md), and [mixer.js](../ui/mixer.md) all re-render from the same object after every mutation.

The effect CRUD functions (`addEffect`, `removeEffect`, `setEffectParam`, `setEffectBypass`, `moveEffect`) take an `effectsOwner` parameter rather than a `Track` specifically — anything shaped like `{ effects: [] }` works, which is what lets `project.master` reuse the exact same functions a track uses, instead of duplicating them. After any of these mutate the data, the caller (currently only [mixer.js](../ui/mixer.md)) is responsible for telling the audio layer ([audio/mixer.js](../audio/mixer.md)) to rebuild the matching runtime effect chain — this file never touches audio nodes itself.

A note's `startBeat` is relative to its containing block, not the project timeline — [transportController.js](./transportController.md) computes the absolute position as `block.startBeat + note.startBeat` when scheduling playback. **Deviation:** every track currently plays through the one global synth patch ([patch.js](../audio/patch.md)) — there is no per-track instrument yet, so all tracks sound identical. Per-track patches are deferred; adding them means both a data-model change here (`Track.patch`) and a way to pick which track's patch the [patchEditor](../ui/patchEditor.md) is editing, which is more UI than "piano roll" scope covers.

`setLoopEnabled`/`setLoopRange` mutate `project.loop`; the caller is responsible for pushing that into the running [transport.js](./transport.md) via `getTransport().setLoop(project.loop)` (done by [timeline.js](../ui/timeline.md)'s `syncLoop()`) — same "data model doesn't touch audio" separation as the effects functions above.

IDs are a simple incrementing counter (`track-1`, `block-1`, `note-1`, ...). Since Phase 9, projects *do* get saved/reloaded ([persistence.js](./persistence.md)) and imported from files ([projectControls.js](../ui/projectControls.md)), so the collision risk this used to just note is now real and handled: `syncIdCounter(project)` scans every id already present in loaded/imported data and advances the counter past the highest one seen — call it once, right after obtaining project data from outside this session, before any `addTrack`/`addBlock`/`addNote`/`addEffect` call.

Every mutator here calls `notifyChanged()` (emits `project:changed` on the [eventBus](./eventBus.md)) — this is what drives autosave in [persistence.js](./persistence.md). Adding a new mutator function without this call means edits it makes are silently lost on reload.

`serializeProject`/`parseProject` are the JSON (de)serialization used for file export/import (same thin-wrapper pattern as [patch.js](../audio/patch.md)'s `serializePatch`/`parsePatch`). `replaceProjectContents(target, source)` deep-clones `source` (a plain object, e.g. freshly parsed from a file or loaded from storage) and overwrites `target`'s fields *in place* — deliberately not swapping to a new object reference, since every UI module ([timeline.js](../ui/timeline.md), [mixer.js](../ui/mixer.md), `transportController.js`) holds onto the original project reference from startup.
