# transport.js

Audio-accurate play/pause/stop/seek clock, independent of any UI. `getPositionBeats()` is computed on demand from `audioContext.currentTime` (it never drifts).

`createTransport(audioContext, { onSchedule, onCancel })`:
- `onSchedule(windowStart, windowEnd, beatToContextTime)` is a lookahead scheduler hook. A poll every 25ms, driven by the worker-based [ticker.js](./ticker.md) so it keeps running in a hidden tab, hands out consecutive, non-overlapping beat windows **0.2 s ahead of real time, 1 s while the tab is hidden** (a `visibilitychange` polls at once). Before 2026-10-15 the horizon was 100 ms, so a stalled renderer meant late notes fired in a burst; 0.5 s was tried next and made the user's glitches worse, because every early-scheduled voice is a live set of nodes on the audio thread for that much longer. The user's machine (a 192 kHz output device, so Chrome resamples everything) is CPU-bound on the audio thread; the "Stable" audio-buffer setting in [audioEngine.js](../audio/audioEngine.md) is the lever for that. The consumer ([transportController.js](./transportController.md)) decides what falls in each window.
- `onCancel()` fires on `pause()`, `stop()` and a `seek()` while running, since everything already scheduled ahead is now wrong.

**`play()` waits for a running context.** If the `AudioContext` is suspended, it calls `resume()` and anchors the clock only once that resolves. Anchoring to a suspended context's frozen `currentTime` would leave the transport "playing" against a clock that never moves. While waiting, `isRunning()` is true, so a second Space press toggles it off, and `isWaitingForAudio()` is true. `pause()`/`stop()` cancel the pending start. It emits `transport:waiting-for-audio` when it has to wait.

`setTempo()` re-anchors the position so changing tempo mid-playback doesn't jump, and it's a no-op for an unchanged tempo. `pause()` freezes the position, `stop()` rewinds to 0, and `seek(beat)` jumps (re-anchoring and resetting the schedule cursor if running). Emits `transport:play/pause/stop/seek/tempo/loop` on the [eventBus](./eventBus.md). The UI polls `getPositionBeats()` for the playhead instead of subscribing.

**Looping (`setLoop`):** `play()` resumes from the current position if it's inside the loop and snaps to `loop.startBeat` only from outside it. Before Phase 13 it always snapped, so Pause -> Play restarted the loop.

**Unwrapped scheduling (2026-10-15):** the clock anchor (`startBeat` at `startContextTime`) never moves at the loop seam. Time since the anchor counts *unwrapped* beats, which run on past `loop.endBeat`; `wrap()` folds them into the loop for `getPositionBeats()`. The scheduling `cursor` lives in the same unwrapped frame, so windows can be handed out any distance ahead, straight through seams: each window stops at the next seam (`nextSeamAfter`), its start is wrapped, and its `beatToContextTime` closure carries the window's unwrapped-minus-wrapped offset. Before this, scheduling was capped at `loop.endBeat` and resumed only after real time crossed it, which left zero margin at every seam. `reanchor()` handles tempo changes (keeping already-scheduled audio and moving the cursor into the new frame, so nothing is scheduled twice or skipped) and seeks/loop changes (cancel, restart from the position). Verified: notes scheduled across 2–3 loop cycles in three demos stayed within the exact expected count, with no late starts, and metronome clicks were exactly one beat apart across every seam.
