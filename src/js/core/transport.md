# transport.js

Audio-accurate play/pause/stop clock, independent of any UI. Position tracking (`getPositionBeats()`) is computed on demand from `audioContext.currentTime`, not incremented by a timer — so it never drifts and stays correct even if the tab is throttled.

`onSchedule(windowStartBeat, windowEndBeat, beatToContextTime)` is the generic "lookahead scheduler" hook (`setTimeout` polls every 25ms; each poll hands the caller a *new, non-overlapping* beat range — `[windowStartBeat, windowEndBeat)` — plus a converter from beat number to the precise `AudioContext` time to schedule at). This is deliberately generic rather than "fires per beat": both the metronome ([transportController.js](./transportController.md)) and the note sequencer (same file) share one poll loop, each deciding for itself what falls in the window and needs scheduling. This is what the plan's "audio-accurate scheduling, not `setInterval` drift" note refers to — nothing about *what* gets scheduled lives here, only *when* to check.

`setTempo()` preserves the current beat position across a tempo change (re-anchors `startBeat`/`startContextTime` first) so changing tempo mid-playback doesn't jump the playhead; `scheduledUpToBeat` (the poll cursor) is left untouched since it's already in beat-space, which a tempo change doesn't affect. `pause()` freezes position; `stop()` resets to beat 0. This module only emits `transport:play`/`pause`/`stop`/`tempo`/`loop` on the [eventBus](./eventBus.md) for anything that wants to react to state changes — the UI polls `getPositionBeats()` directly via `requestAnimationFrame` (plus synchronous calls on its own control actions — see [timeline.js](../ui/timeline.md)) for the playhead instead of subscribing, since that needs to run continuously, not just on state-change events.

**Looping (`setLoop({ enabled, startBeat, endBeat })`):** `play()` snaps the start position to `loop.startBeat` when a loop is active. During playback, `poll()` detects when a single poll's lookahead window would cross `loop.endBeat` and splits that one call into two `onSchedule` invocations — one for the pre-wrap remainder up to `loop.endBeat`, one for the post-wrap segment starting at `loop.startBeat` — re-anchoring `startBeat`/`startContextTime` to the *exact* `AudioContext` time the wrap occurs (via `beatToContextTime(loop.endBeat)`, computed *before* the reset) so both segments' scheduled audio times stay sample-accurate across the seam; nothing is retroactively rescheduled or clipped. `getPositionBeats()` additionally wraps its own raw computation as a safety net for the up-to-25ms gap between actually crossing the loop end and the next `poll()` tick catching it — this only affects reads (the UI playhead, `pause()`), never the scheduling math in `poll()` itself, which always re-anchors from its own precise crossing check.
